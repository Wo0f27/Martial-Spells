# Archers Ranger AR1 — shared foundation and target calibration

This checkpoint implements neutral helpers only. `ARCHERS_RANGER_SPELL_PORT.md` remains the frozen source/translation contract. AR1 adds no spell, effect, projectile entity, renderer, asset, dependency, set detector, or ability executor. Existing Barrage, Entangling Arrow, and Caltrops classes and registration are unchanged.

## Evidence and cooldown decision

The target artifacts examined were Iron's Spells `1.20.1-3.16.3`, Apothic Attributes `1.20.1-1.3.7`, RWA Forge `1.1.4-forge-private.1`, and Forge `1.20.1-47.4.10` mapped with Parchment `2023.09.03-1.20.1`. Iron's locally cached runtime class bytecode was checked with `javap -c -p` (`MagicManager`, `AbstractSpell`, `Utils`, `SpellCooldownAddedEvent.Pre`, and cooldown attribute registration). Apothic's matching source jar supplied `AttributeEvents.arrow`; RWA's frozen local source supplied `ScalingUtil` and bow/crossbow mixins. Mapped Forge classes supplied `BowItem`, `CrossbowItem`, `ArrowItem`, `AbstractArrow`, `Entity`, and living/player attributes.

Iron's Cooldown Reduction is a percent-style attribute whose neutral effective value is **1.0**. For a normal cast, `AbstractSpell.getSpellCooldown()` truncates configured seconds × 20 to base ticks. `MagicManager.getEffectiveSpellCooldown` calculates `(int)(baseTicks × (2 - Utils.softCapFormula(CDR)) × sourceMultiplier)`, truncating toward zero. `softCapFormula(x)` returns `x` through 1.5 and `2 - 0.25/(x - 1)` above 1.5. The source multiplier is normally one; Iron's sword cast source uses its configured sword multiplier. `MagicManager.addCooldown` computes this value, posts `SpellCooldownAddedEvent.Pre`, then stores and syncs the **event's** effective tick value if the event is not cancelled. Setting a fixed value in Pre therefore replaces Iron's ordinary reduction for that cooldown. Other event handlers could still mutate/cancel the event according to their priority/order; AR5 must choose a final handler priority and test integrations.

The five non-Wolf Archers-derived spells use ordinary Iron's effective cooldown. This is the target semantic analogue of Spell Engine haste, **not** numerical equality: source Spell Power divides a post-deduction duration by haste, while Iron's multiplies ticks by its soft-capped CDR expression and can include a cast-source multiplier. Spirit Wolf's later Pre handler must set `SpiritWolfFixedCooldown.ticks(0) = 900` (or `ticks(100) = 800` for the future narrow equipment adapter), excluding ordinary CDR. AR1 installs only the neutral arithmetic, no spell handler or equipment detection. Existing Barrage's fixed six-second handler remains untouched until AR3.

## Arrow creation, scaling, and event order

For ordinary bow shots, vanilla creates an `AbstractArrow` through the ammunition `ArrowItem.createArrow`, then `BowItem.customArrow`, shoots it, sets full-draw critical, adds Power (`0.5 × level + 0.5`) to base damage, sets Punch knockback and Flame fire, then calls `addFreshEntity`. Vanilla crossbow loading similarly uses `ArrowItem.createArrow`; launch sets a critical flag for player shots and Piercing from the crossbow enchantment before spawn. This preserves ammo-specific projectile classes, including spectral and tipped arrows. RWA's bow/crossbow mixins wrap ordinary weapon spawn and scale arrow base damage **before** `addFreshEntity`; they do not see a projectile created and spawned independently by a spell.

`ArchersPhysicalArrow.prepare` is that separate future spell path. It requires supported weapon and real ArrowItem ammunition, preserves the ammo-created projectile and bow customization, applies relevant vanilla enchantment state, old-RWA ratio once, then a supplied technique multiplier once. It accepts explicit critical, knockback, iframe and extra-pierce-target settings; `launch` applies the supplied speed before the caller spawns the arrow. It never reads Martial Power, Iron's spell power, or Apothic Arrow Damage. The caller owns ammunition payment and successful `addFreshEntity`; AR3 will decide the exact consume/Infinity branch at each of the three physical launches. No current spell calls this path.

Apothic's server `EntityJoinLevelEvent` handler (normal priority) sees any `AbstractArrow` after `addFreshEntity` begins and before the arrow's first movement/collision tick. Its persistent `attributeslib.arrow.done` marker prevents reapplication. It multiplies base damage once by the owner's effective `ARROW_DAMAGE` and multiplies motion once by `ARROW_VELOCITY`. The old-RWA ratio and technique multiplier must therefore be complete **before** spawn, and AR3 must not multiply by nominal P. On a later arrow tick, Forge's `ProjectileImpactEvent` fires for a collision before `AbstractArrow.onHitEntity` calls `target.hurt`; target invulnerability affects that later damage call. An iframe reset in the impact event must check actual eligibility/cancellation carefully. Event handlers at the same priority, including existing deflection logic, may affect the outcome; AR3 will wire the marker to a narrowly filtered hit handler rather than global iframe resets.

Vanilla `AbstractArrow.onHitEntity` computes `ceil(baseDamage × current speed)`, then adds a random critical bonus when critical is set; defenses and other damage hooks follow. Piercing uses a signed byte level `N` and tracks already-hit entity IDs. It can hit **N + 1 distinct entities**, adding each ID to the ignore set and refusing repeat hits; it discards before an additional entity once the set size reaches `N + 1`. Therefore a future `+1 target` means **increase pierce level by one**, subject to byte capacity, not set pierce level to one unconditionally. `ArchersPhysicalArrow` rejects a total above 127. Projectile hit history is vanilla runtime state, so AR3 must verify save/reload implications for any long-lived piercing arrow.

## Nominal ranged power

`NominalPhysicalRangedPower.get(caster)` chooses a supported main-hand bow/crossbow, otherwise a supported offhand weapon. `W` is positive `RangedConfig.damage`, otherwise 6 for a bow or 9 for a crossbow. `A` is `max(0, effective Apothic ARROW_DAMAGE)` (neutral 1 if the caster has no such attribute). `P = W × A`. For **no supported weapon**, W deliberately falls back to neutral bow damage 6, so Wolf owner scaling and other non-arrow executors have a deterministic target value; a null caster likewise gives P=6. This is a target convention, not a claimed source unarmed value. It does not include Arrow Velocity, critical, Power/Punch/Flame/Piercing, Iron's spell power or Martial Power. Rain, Magic Arrow, and Wolf may use P at their source-defined sampling points; Barrage may not.

## Projectile state and deadlines

`RangerArrowMetadata` stores a versioned-by-key compound in Forge `Entity.getPersistentData`, which the entity save path serializes as `ForgeData`. It carries an eligible-shot marker, per-identity transfer payloads with duplicate-stamp rejection, an iframe-bypass marker, and neutral extra-pierce-target count. AR2 will define the exact Power Shot eligibility and transfer trigger, including vanilla shots; AR3 will consume the iframe and pierce metadata. No event reader or effect application is installed now. Metadata is server-authoritative and does not require client sync for hit decisions.

`JudgementImpactManager` persists a single per-player pending impact and cannot represent Rain's repeated launches plus Wolf's independently delayed second summon. `RangerTickScheduler` provides a small server-only, tick-deadline queue keyed by server instance, dimension and caster UUID. It supports cancellation by job or caster and clears jobs at server stop. The callback receives a `ServerLevel` and caster UUID; it decides whether the caster must still be alive (Rain) or a prepared summon may spawn (Wolf). The queue itself is transient. AR4/AR5 must persist **ability-specific** pending descriptors and rehydrate them when reload robustness is needed; this generic queue does not claim persistence or source parity by itself.

## Control, relations, and presentation

Roots' physical-melee application threshold will reuse `PhysicalMeleePower.controlHealthLimit`, not P. Existing friendly/allied tests in the combat helpers and `LivingEntity.isAlliedTo`/owner checks should be reused at each ability's target filter; no generic relation rewrite is warranted in AR1. Entangling Arrow's existing Iron's RootEntity behavior is untouched. The current effects registry, entity spawn/network patterns, particle/sound registry, renderer hooks, and client animation hooks can host AR2–AR5 presentation. The existing Iron's Magic Arrow pose hook is explicitly tied to `irons_spellbooks:magic_arrow`; later Ranger presentation must add its own ID. No neutral presentation registration was needed before a real asset/entity exists.

`Attributes.JUMP_STRENGTH` exists in mapped 1.20.1 but is absent from ordinary `LivingEntity` and `Player` default attribute suppliers; horses include it. AR2 will attach the source -50% `MULTIPLY_BASE` modifier where the target has Jump Strength. For ordinary affected living entities, AR2 should use a Roots-scoped `LivingJumpEvent` to scale the initial upward jump motion by 0.5 while the effect is active. That is the closest local expression of the *authored* jump reduction, and is an intentional target behavior for entities on which the source attribute modifier cannot attach. It must be checked against other movement modifiers and must not modify Entangling Arrow's RootEntity.

- **AR3:** migrate the single existing Barrage ID, settle per-shot ammo/Infinity behavior, tag its arrows, verify cancelled/deflected impact handling and piercing across save/reload; remove the current six-second fixed handler only then.

## Power Shot shot and hit semantics

**Eligible shot rule.** The final vanilla bow arrow is tagged immediately after `BowItem.customArrow` in `BowItem.releaseUsing`; a vanilla crossbow arrow is tagged at each `CrossbowItem.getArrow` call. These paths include ammunition variants and separate multishot projectiles without relying on the player's held item at join time. AR1 `ArchersPhysicalArrow.prepare` already tags future ammo-created Ranger spell arrows. Existing `EntanglingArrow` is an explicit physical-arrow class recognized at join without editing its gameplay file. An `EntityJoinLevelEvent` spends a charge only for an `AbstractArrow` owned by a `ServerPlayer` and carrying one of those exact origin identities. Dispenser/ownerless arrows, other players' stash, and non-arrow projectiles are excluded. A third-party bow that overrides vanilla release without calling either creation path must explicitly tag its arrow; this is an integration boundary rather than an owner/held-item guess. **Current pre-AR3 BarrageArrow is intentionally excluded** because its separate impact handler permanently clears target iframes; accepting it here would violate Power Shot's save/restore rule without changing Barrage code. AR3's migration to the AR1 ammo helper will tag its arrows automatically. This is a temporary target integration gap, not a reinterpretation of source `ARROW_SHOT`.

The caster receives vanilla-persisted `power_shot_stash` for 240 ticks at amplifier 2, which is three effective charges. At `EntityJoinLevelEvent.LOWEST`, a noncancelled eligible spawn saves `shotEvaluated` on that projectile even when no stash is active, so a rejoin cannot spend a later cast. One transfer per projectile is saved under the `power_shot` key; one charge is consumed immediately by replacing amplifier 2→1→0 and then removing the effect, preserving the original remaining duration. A missed projectile keeps its spent charge. The transferred state, iframe marker, shot-evaluated marker and per-target hit UUIDs live in Forge entity persistent NBT. They survive arrow reload independently of the caster stash. MobEffectInstance NBT preserves stash and Hunter's Mark duration/amplifier across player/entity reload. A mod cancelling join after our LOWEST listener would still spend a charge; same-priority listener ordering is a residual cross-mod boundary for runtime integration.

**Damage order.** Mapped Forge `LivingEntity.hurt` invokes `ForgeHooks.onLivingAttack` at entry, then immunity/shield and iframe checks, then `actuallyHurt`; `LivingHurtEvent` is inside the latter and cannot change the amount before iframe comparison. `LivingDamageEvent` is later still. `LivingEntityHuntersMarkMixin` changes only the incoming float at `hurt` HEAD and only when Hunter's Mark is present on the server: `amount × (1 + 0.1 × (amplifier+1))`. This reaches all damage sources that enter `LivingEntity.hurt`, before defense and existing Martial `LivingHurtEvent`/`LivingDamageEvent` hooks. Apothic's `LivingAttackEvent`/`LivingHurtEvent` handlers then observe the scaled amount; its `LivingHurtEvent` critical modifier (HIGH) is applied later. This preserves source-style damage-entry semantics, subject to other mods with their own `hurt` HEAD mixins and Forge cancellation.

**Iframe and impact order.** Forge's projectile impact event runs before `AbstractArrow.onHitEntity`; cancellation prevents the latter and therefore prevents the mark. `AbstractArrowPowerShotMixin` redirects only the actual `Entity.hurt` call in `onHitEntity`. `PowerShotImpact` checks the projectile's transferred spell key, saves the target's previous `invulnerableTime`, temporarily sets it to zero, calls normal `hurt`, then restores the exact prior value in `finally`. It applies the transferred mark after that call even when damage returns false, matching source transfer behavior. A saved per-arrow/target UUID guard prevents duplicate mark applications, including after arrow reload. Unrelated arrows pass through the same invocation unchanged.

The first mark hit applies amplifier 0, then 1, then 2; additional hits remain at 2 and refresh to 240 ticks. Mark is never a projectile damage multiplier. Ordinary effect NBT saves the stack and duration.

## Entangling Roots cloud

The cloud is a stationary server-owned Forge entity of width 7 and height 1.05, placed at the caster, with explicit owner UUID and `ageTicks` NBT. Server tick increments age first. It attempts impacts exactly at ages 15, 30, 45, 60, 75, 90, 105, 120, 135, and 150; age 160 discards before any pulse. Saving/restoring `ageTicks` preserves remaining life and pulse phase, preventing a reload from restarting the eight seconds. A missing/offline/out-of-dimension owner causes due pulse attempts to do nothing; the cloud still ages. This is a target persistence improvement over source cloud NBT.

The candidate search begins with the cloud AABB expanded vertically by `3.5 × 0.3 + 0.5 = 1.55`, then checks target center distance ≤3.5. The default source harmful-area relation admits neutral/hostile entities but excludes the caster, allied teams, players, villagers, allays, iron golems, cats and tamed animals, following Spell Engine's default relation configuration. Visibility uses block-collision rays to the target center or the nearest point on its AABB. Solid walls therefore block the effect. The target gate is inclusive: `target.maxHealth <= 50 + 5 × PhysicalMeleePower.get(caster)`.

**Power sampling.** Exact Spell Engine `SpellCloud.tick` calls `SpellImpacts.lookupAndPerformAreaImpact` at every due pulse. `SpellImpacts` resolves the impact's physical-melee attribute for that evaluation, overriding any cached school power in the context. AR2 therefore reads the owner's current `Attributes.ATTACK_DAMAGE` on each pulse, not once at cast; no nominal ranged P is involved.

Each qualifying pulse SETS amplifier-zero Roots for 20 ticks. Its effect supplies `-0.5 MULTIPLY_BASE` Movement Speed and Jump Strength. Mapped Forge `MobEffect.addAttributeModifiers` skips an attribute absent on a target. Horses and other entities with Jump Strength use that direct modifier. For ordinary players/mobs, `LivingJumpEvent` subtracts 0.21 from the vertical launch only while Roots is active, corresponding to half vanilla's 0.42 base jump. The event fires after `getJumpPower()` and sprint motion; subtracting a fixed base portion leaves Jump Boost's additive height instead of halving it. An entity with a customized base jump and no Jump Strength attribute gets an approximation; the source-authored attribute cannot represent that case on this target. Removing Roots immediately removes both the attribute and event condition. Entangling Arrow's hard RootEntity path is untouched.

**AR4 presentation-only correction:** the source's 0.5 playback speed gives the eight-frame stripe a nominal **32-tick** lifetime (`16/0.5`), whereas the initial AR2 provider used 16 ticks. `RangerSourceParticle` now uses 32 with the same 50% lifetime spread. Exact source `StatusEffect.show_particles=false` was also missed for Hunter's Mark; `PowerShotImpact` now suppresses only the generic vanilla status-effect motes. The Roots cloud now emits two exact 14-frame `roots` sprites every active tick, randomly across the full 3.5-block cloud radius at 0.1 cloud height. Vanilla firework/spore providers are reused directly. Iron's instant-cast pose is the established local animation analogue rather than the Spell Engine animation file. ### Hunter's Mark visual follow-up

The developer confirmed every AR2 mechanic and the rest of the presentation at runtime, but the actual Hunter's Mark model was invisible. Frozen Archers `ArchersClientMod` registers `HuntersMarkRenderer` for the synchronized `archers:hunters_mark` effect. Spell Engine's `LivingEntityRendererMixin` at render TAIL loops synchronized effects and invokes that renderer once per effect, excluding the local player's first-person body. The renderer rejects dead targets, then offsets horizontally toward the camera by `entity.width × 0.5`, rises to `entity.height × 0.75` (1.20.1 entity scale is 1), rotates Y by `180° + atan2(cameraDirection.x, cameraDirection.z)` and X by camera pitch, then draws the exact `hunters_mark` baked model on Spell Engine's `GLOW` beacon-beam layer. It has no time animation and does not use amplifier. Removal of the synchronized effect ends rendering.

The local `HuntersMarkEffectRenderer` already had the exact private-use model/texture and these transforms; `ModelEvent.RegisterAdditional` registered the model ID. Neither its earlier beacon layer nor a full-bright block-atlas cutout layer produced a visible mark in the user's runtime tests. The earlier client `getEffect` gate was not equivalent to Spell Engine's synchronized-effect lookup on observed mobs. The narrow observer-sync translation below replaces that gate without changing the model or material.

#### Accepted observer sync fix

The developer's 2026-10-01 `run/logs/latest.log` proved client hook registration and a `RenderLivingEvent.Post` callback for an iron golem (`clientSide=true`). Model baking reported `missing=false`, **54 general quads, 0 directional quads**, and both particle and first-quad sprites as `martial_spells:spell_effect/hunters_mark` on `minecraft:textures/atlas/blocks.png`. That log ended immediately after the first golem callback, so it did not prove client-side effect presence at the later hit. The screenshot supplied afterward establishes the desired small red targeting structure in front of the upper body, not the result of a target-side probe.

Exact source explains why a mob-effect HUD result cannot drive the target renderer: Spell Engine's `LivingEntityStatusEffectSync` writes selected effect IDs to a tracked living-entity data field; its render-tail mixin reads `Synchronized.effectsOf(entity)`, not the ordinary client `activeStatusEffects` map. The target Forge 1.20.1 `LivingEntity.sendEffectToPassengers` sends `ClientboundUpdateMobEffectPacket` only to player passengers; normal observers of a mob do not receive each effect instance as renderer state. The target renderer's previous `entity.getEffect(HUNTERS_MARK)` gate therefore had no reliable mark identity for an observed iron golem even though the server had applied the effect. This is a source/target synchronization-path defect, not evidence for another render-layer change.

`LivingEntityHuntersMarkVisualMixin` defines **one Boolean SynchedEntityData field** on `LivingEntity`. On the server it mirrors only the presence of `martial_spells:hunters_mark` after effect add, refresh, removal, and NBT load. Minecraft's entity tracker sends that value to clients already tracking or newly tracking the entity. `HuntersMarkEffectRenderer` reads this tracked visual flag; it still excludes only the local first-person self, draws the exact 54-quad baked source model through the block atlas at full brightness, and retains source placement/orientation and one draw per marked entity. The tracked field has no effect on damage, stacking, duration, iframe behavior, hitbox, or other spells. All one-shot logs, magenta quad, and oversized model probes were removed. The user confirmed the world-space marker at runtime; the assistant did not run Minecraft.

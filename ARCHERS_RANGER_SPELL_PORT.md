## Current Ranger implementation and reusable systems

At the target base, `MartialSpellRegistry` registers exactly three Ranger spells: Barrage, Entangling Arrow, and Caltrops. Each implements `MartialTechnique` with `MartialTechniqueClass.RANGER`; `MartialTechniqueTags.RANGER_TECHNIQUES` and `data/martial_spells/tags/spells/ranger_techniques.json` list those three. The school is `martial_spells:martial`; `MartialPowerHelper` is its existing multiplier, not automatically a source physical-ranged-power adapter. `RangedWeaponClassifier` checks the Martial bow/crossbow tags before item inheritance, including equipment-port/Forge tool tags. `RangedTechniqueHelper` chooses main hand before offhand, copies bow Power/Punch/Flame or crossbow Piercing, applies old-RWA configuration ratios, then Martial Power, and creates the existing custom arrow entities.

`BarrageSpell` currently has five levels, 2/3/3/4/5 arrows, 0.5/0.625/0.75/0.875/1.0 multipliers, shots four ticks apart after ten ticks of preparation, and a forced six-second cooldown. `BarrageArrow` is an `AbstractArrow` with Forge spawn packet, inherited arrow save state, no pickup, block discard, and a custom trail; `BarrageProjectileEvents` clears `invulnerableTime` on entity impact. `EntanglingArrowSpell` is a 20-tick cast with a 15-second base/seven-second cooldown floor, level-dependent 2–6-second Iron's `RootEntity`, and its own saved projectile root duration. Caltrops uses an instant thrown `CaltropBundleProjectile`, a server-owned `CaltropFieldEntity`, level-dependent field/damage/slow/lifetime, owner UUID, entity data, and saved remaining life. These are separate behaviors and must receive regression coverage in AR6.

Reuse the existing `PhysicalMeleePower` (`Attributes.ATTACK_DAMAGE`), `MartialEntityRegistry`/client renderer registration/`NetworkHooks`, `MartialEffectRegistry`, `MartialNetwork`, the projectile/field owner-save patterns, `JudgementImpactManager`'s server-timed meteor pattern, `RangedTechniqueCooldownEvents`/`PaladinP4Events`' cooldown Pre hook, and current spell-cast/client animation hooks where their timing fits. Existing `MagicArrowClientVisuals` recognizes Iron's Magic Arrow, Barrage and Entangling Arrow and drives weapon poses; add the new identity deliberately later instead of treating Iron's Magic Arrow as the new spell. Existing Barrage icon/trail and Iron's Magic Arrow art are not source-presentation evidence.

## Shared translation decisions

**Mana/resources.** All six target spells start at `baseManaCost = 0`, `manaCostPerLevel = 0`, matching the existing Ranger/Rogue/Warrior Martial technique convention. This is an **intentional target divergence**, not source resource parity. Spell Engine has no implicit numeric mana, but its `Cost` defaults to 0.1 exhaustion and one point of spell-host durability per successful cast; Roots explicitly raises exhaustion to 0.2. Both default costs are absent from the target Martial technique policy. A damageable source item/held item takes durability when enabled; a nondamageable one does not. Arrow costs are distinct: Barrage's spell item check has `consume=false`, but its three physical launches each load an arrow (see AR0.1 closure). Magic Arrow's omitted `consume` is **true**, so a successful release spends one arrow by default, subject to creative/Infinity/server-config exemptions. The other four declare no arrow item cost. A ranged-weapon item requirement is a distinct target validation decision: Barrage needs a bow/crossbow for physical launch; Ranger visual/weapon semantics favor requiring one for Rain and Magic Arrow, but the source spell cost alone does not prove a blanket weapon gate for Power Shot, Roots or Wolf.

**Spell levels.** All six Archers-derived targets initially have `maxLevel = 1` and fixed source coefficients/counts/durations. Source tiers are unlock metadata, not a five-level progression formula. Barrage's current five-level count/damage design is explicitly retired at AR3 while its ID remains. Existing player data with Barrage level 2–5 needs a deterministic clamp/display/binding migration check at AR3; AR0 does not edit data. Entangling Arrow and Caltrops retain their independent five-level models. Any later multi-level balance design is a separate redesign, never an inferred Archers port.

**Cooldowns.** Exact Spell Engine `Cost.Cooldown.haste_affected` defaults to `true`, and its server-wide `haste_affects_cooldown` defaults to `true`. Thus Power Shot, Roots, Barrage, Rain and Magic Arrow all receive source Spell Power haste after any spell-specific cooldown deduction; source duration is `(base seconds - deduction) / haste`, floored at zero and rounded to ticks by the cooldown manager. Iron's ordinary cooldown reduction remains the target analogue for those five, but its numerical formula must be compared at AR1 rather than asserted identical. Wolf explicitly sets `haste_affected=false`: set its Iron's effective cooldown in `SpellCooldownAddedEvent.Pre` to a local exact base of 900 ticks, minus only the future narrow Armory adjustment; ordinary cooldown reduction must not shorten it. This deliberately excludes Spell Engine's possible generic spell-specific cooldown deduction for Wolf. Remove Barrage's current forced six-second/no-reduction rule in AR3; a ten-second base is nonnegotiable.

**Scheduling and cancellation.** Iron's cast state is not an impact scheduler. Server-only jobs must carry caster UUID, dimension and target identity/location as needed. Pre-release interruption cancels a normal cast without cost; a charge cast below its release threshold also fizzles without cost. Spell Engine imposes cooldown, exhaustion, durability and spell item cost only from a successful delivery callback. Its scheduled launches are in-memory world runnables, lost on restart; later meteor/arrow launches check caster alive, while a prepared delayed wolf spawn does not. A target entity is re-read at each delayed meteor launch rather than position-snapshotted at release. Target implementations should deliberately preserve or improve reload behavior as stated per ability below, and document any improvement as a divergence. Do not send client authority for hits, damage or AI.

## Physical-ranged calibration and event order

**Two named quantities are required.** A physical arrow's hit is not equal to a spell-power coefficient times configured weapon damage. Vanilla `AbstractArrow` starts with base damage and derives collision damage from motion, with critical, enchantment, piercing, knockback, target defenses and other events afterward. The target RWA 1.1.4 `ScalingUtil` has bow baseline `(velocity 3, damage 6)` and crossbow `(3.15, 9)`; for configured `W` and velocity `V > 0`, its base-damage multiplier is `(W / baselineDamage) * (baselineVelocity / V)`, or just `W / baselineDamage` when V is unset. The compensation neutralizes *configured* velocity's inherent damage effect; it does not cancel Apothic `ARROW_VELOCITY` or a technique's explicit launch speed. Bow/crossbow mixins apply this ratio before `addFreshEntity` for ordinary weapon shots, but **they do not run when MartialSpells directly creates a custom arrow**. `RangedTechniqueHelper` therefore applies the ratio itself to its custom arrows.

Apothic Attributes 1.3.7's `AttributeEvents.arrow(EntityJoinLevelEvent)` then multiplies any server-side `AbstractArrow` base damage by owner `ARROW_DAMAGE` and scales motion by owner `ARROW_VELOCITY`, guarded by persistent `attributeslib.arrow.done`. This was checked in the locally cached 1.3.7 class bytecode. The equipment port's armor adds `ARROW_DAMAGE` modifiers; target RWA itself does **not** register source `ranged_weapon:damage`. RWA's old reference attribute has base zero and the held weapon contributes its configured damage as an additive modifier. The source's newer RWA 2.3.4 exact attribute modifier evaluation is not available in the supplied repositories, so numerical equivalence to every possible source equipment/other-mod modifier remains unproven.

The accepted equipment-port registry currently configures bows at W=8/8/10/9/12 (Composite, Mechanic, Royal, Netherite Short, Netherite Long) and crossbows at W=8.5/13/9.5/15 (Rapid, Heavy, Netherite Rapid, Netherite Heavy), all with velocity configuration zero. Archer armor pieces add `+0.05` each to Apothic `ARROW_DAMAGE` with `MULTIPLY_BASE`; Ranger pieces add `+0.08` and Netherite Ranger pieces `+0.10`. `DRAW_SPEED` modifiers on Ranger gear affect drawing, not P. These are equipment-port values, not spell coefficients.

Freeze a target `NominalPhysicalRangedPower(caster, selectedWeapon)` for **non-AbstractArrow spell damage and Wolf owner scaling**: `W = positive RangedConfig.damage, else 6 for bow / 9 for crossbow`; `A = max(0, effective Apothic ARROW_DAMAGE)` with neutral 1; `P = W * A`. Read the selected main-hand-first weapon at the source-equivalent power-sampling point, and define a null/unarmed fallback explicitly before implementing Wolf when no supported weapon is held. This is a coherent **target-stack analogue**, not proof of byte-for-byte equality with modern source RWA's attribute. It has damage units and incorporates the equipment port's arrow-damage bonuses. It excludes `ARROW_VELOCITY`, Power/Punch/Flame/Piercing, crit, Iron's spell power and `MARTIAL_SPELL_POWER`. Rain and Magic Arrow calculate source coefficients from P directly in their local non-arrow executor; they must **not** pass through Apothic's arrow join multiplication afterward.

Freeze a separate `PhysicalArrowBase(caster, weapon, projectile, techniqueMultiplier)` path for Barrage: start from the chosen vanilla-like arrow base/enchantment state, apply RWA's configuration ratio exactly once, apply `0.75` exactly once, spawn the `AbstractArrow`, then let Apothic multiply its base damage by A **exactly once** on join. Do not also multiply by P or Martial Power. Preserve vanilla-derived critical roll, bow enchantments, crossbow Piercing, target defenses and velocity's collision contribution; set the source 3.15 launch speed even for bows. Existing helper order adds Power enchantment before the ratio, matching the existing custom-arrow behavior; AR3 must compare that order with vanilla/RWA's actual shot construction, including ammo-created arrow variants. The current helper's Martial Power multiplication is a divergence to remove for Archers Barrage only, not a reason to alter Entangling Arrow. Existing `ProjectileImpactEvent` iframe reset occurs before arrow hit; the later implementation must ensure it only resets for valid targets and does not unintentionally alter a failed/cancelled hit. Iframe bypass belongs on the Barrage/Power Shot tagged arrows, not globally.

Current Barrage base-damage setup is `(initial AbstractArrow base damage + bow Power bonus, if any) × RWA configuration ratio × level-dependent technique multiplier × MartialPower`; crossbow Piercing is assigned before scaling. At `addFreshEntity`, Apothic then multiplies that result by A once and its velocity factor changes later collision damage. The desired source translation changes the technique multiplier to fixed 0.75, removes MartialPower, and retains the one Apothic join multiplication. `P = W × A` must never be multiplied into this result; doing so would apply weapon damage and A twice.

**Worked neutral calibration:** bow W=6, A=1 gives P=6; crossbow W=9 gives P=9. An equipment `ARROW_DAMAGE` effective value of 1.10 gives P=6.6 or 9.9. This does not assert those are final vanilla arrow hit numbers. Source Wolf scales from a ranged-damage attribute in nominal damage units; it should use P, while Barrage uses the arrow pipeline.

## Ability baselines and implementation contracts

### Power Shot — `archers:power_shot` → `martial_spells:power_shot`

Instant, tier 2 marksman, source range 0, eight-second cooldown, no launched spell projectile, no authored velocity/count/pierce/knockback/direct damage coefficient or ammunition cost. Release plays `archers:marker_shot` at 0.5 volume with floating red magic-stripe particles. Source `STASH_EFFECT` gives the caster `hunters_mark_stash` for 12 seconds at amplifier 2, listens for `ARROW_SHOT`, and transfers its impacts to shot arrows. Each qualifying arrow hit adds a 12-second `hunters_mark` at increment 1, cap 2; mark modifies Spell Engine `damage_taken` by `+0.1` `MULTIPLY_BASE` per effective effect level, and impact emits firework particles. Tagged arrows bypass target iframes. The source does not author a replacement arrow or piercing bonus.

Later implementation belongs in one `INSTANT` spell, caster stash and target mark mob effects/state, and shared Ranger arrow-shot/projectile-hit events. The source stash's amplifier 2 means **three shot-trigger charges**; each `ArrowHelper.onArrowSpawned` call fires `ARROW_SHOT` (ordinary or spell-fired, because the authored trigger has no `from_spell` filter), stamps Power Shot onto that one arrow, and immediately reduces the stash amplifier by one. A miss still spends that charge. A normal multishot can spend several charges, one per spawned arrow; the spell-ID stamp guard prevents the same spell from being applied twice to one projectile. Remaining duration is preserved on decrement, and the caster's ordinary status-effect NBT preserves remaining charges/expiry. The tagged arrow's spell IDs are saved and data-tracked, so its later hit can apply the mark after the caster stash expires. Mark ADD amplifier 1 starts at effect amplifier 0, then rises 1 and 2, with cap 2 and 12-second duration refresh on later hits; effective effect levels are 1/2/3, hence the configured `+0.1 MULTIPLY_BASE` gives +10%/+20%/+30% damage taken, subject to other source modifiers. Spell Engine's `LivingEntity.damage` HEAD mixin scales the incoming damage argument by `damage_taken / 100` before the ordinary damage body, so the source mark affects all such damage rather than arrow damage alone. The arrow mixin clears target iframes immediately around the vanilla damage call, restores the previous iframe value afterward, and applies transferred impacts even when vanilla damage reports failure. Apply damage-taken amplification for **all damage sources** in a correctly ordered Forge damage event; do not encode the mark as an arrow-only damage bonus. Exact cross-mod Forge damage-event ordering remains a target integration gate. Current `BarrageProjectileEvents` demonstrates the pre-impact iframe hook, but its Barrage-only code is not a generic Power Shot implementation.

### Entangling Roots — `archers:entangling_roots` → `martial_spells:entangling_roots`

Instant, tier 2 nature, source school **physical melee** with secondary archetype ANY, range 0, 18-second cooldown, explicit 0.2 exhaustion. Release uses `spell_engine:one_handed_area_release`. A self-centered cloud has radius 3.5, vertical-range multiplier 0.3, lasts eight seconds and applies impacts every 15 ticks. Each qualifying pulse **sets** a one-second Roots effect; Archers' `ArcherEffects.java` config declares `-0.5 MULTIPLY_BASE` on both movement speed and jump strength. Whether the jump-strength attribute is attached to a given Minecraft 1.20.1 target is an entity-attribute integration check, so do not silently drop the authored modifier. Application gate compares target **maximum health** against `50 + 5 * noncritical physicalMeleePower`, using the existing `PhysicalMeleePower.get(caster)` = current `Attributes.ATTACK_DAMAGE` as the target analogue, **never P**. It emits root-pillar cloud particles, falling-spore impact particles and `archers:entangling_roots` sound; `RootsRenderer`/model/texture supply the visible root effect. There is no physical arrow, damage coefficient, ammo, velocity, piercing, knockback or summon.

Use a server-owned local cloud with saved caster/owner, remaining duration and tick cadence, plus a local movement-speed mob effect and synchronized presentation. Reuse `PhysicalMeleePower` and field/lifetime patterns, but do not reuse Entangling Arrow's Iron's `RootEntity`: its immobilization and single-arrow geometry change the source. Exact source pulses are at cloud ages 15, 30, …, 150 (ten attempts), not at placement or age 160; source max-health gate is inclusive (`target.maxHealth <= 50 + 5 * noncritical physical-melee power`). The area finder uses a 3.5-block spherical center-distance check after an expanded cloud-box prefilter, with vertical expansion `3.5 * 0.3 + 0.5` and obstacle raycasts to center or nearest box point. The cloud's own entity dimensions are width 7 and height 1.05. Spell Engine saves age/lifetime/spell/cloud modifier but omits owner UUID and impact context, so a reloaded cloud cannot pulse authoritatively; target owner/context persistence intentionally repairs that source limitation.

### Barrage — `archers:barrage` → existing `martial_spells:barrage`

Tier 3 marksman, physical ranged, range 0, ten-tick/0.5-second pull, **one release** with `extra_launch_count=2` = **three total** aimed arrows. Each has source velocity 3.15, arrow damage multiplier 0.75, iframe bypass and knockback 0.5; the first launch has zero spread and the two follow-ups use `ShootArrow.divergence=5`. No source bonus pierce/homing/area/TTL is authored. It requires an arrow item with spell-cost `consume=false`, but exact `ArrowHelper.load` consumes **one physical projectile item per launched arrow** from a container or inventory unless creative or a plain-arrow Infinity bow applies; the source therefore normally consumes three arrows. With fewer than three, later launches return without spawning, while the delivery can still have succeeded and incurred cooldown. Extra launches use zero-tick scheduled callbacks after the first; all three occur within the same release tick when the caster remains alive. Source default haste affects its ten-second cooldown. Cast uses ranged-weapon `spell_engine:archery_pull` and `archers:bow_pull`; release uses `spell_engine:archery_release`. No source Barrage-specific trail/model, spell impact sound or bespoke packet exists. Physical arrow collision and ordinary ammo/enchantment effects are inherited from Spell Engine/weapon machinery.

AR3 migrates **the existing ID in place** from timed 2–5 sequential shots and six-second fixed cooldown to three same-release shots and source scaling. Use Iron's `LONG` cast UI, release callback, server-spawned arrow(s), shared ammo validation and the arrow pipeline above. Validate one arrow at cast/release, then load up to three individual physical arrows at release, preserving partial-volley behavior. Abort before release on interruption; do not fire partial shots during cast ticks. Existing `BarrageArrow`/Forge spawn packet can be retained only if its pickup, piercing, iframe, hit/crit/enchantment, arrow-count and visuals pass source comparisons. Git history supports the identity: `f07f738a64468a71637815192734e1e25dab551c` introduced a three-arrow/0.75/ten-tick/ten-second Barrage; `62abb97`, `9725a0c`, and `7800501` later introduced sequential/level-scaled/six-second behavior.

**Future Strider 4-piece hook:** accept one *extra penetrable target* as a small integer before arrow spawn and combine it with any baseline Piercing enchantment. In vanilla `AbstractArrow`, pierce level N permits the first target plus N further target pierces, so `+1 target` means `newPierceLevel = baselinePierceLevel + 1` (e.g., 0 → 1 permits two total), not `+2` and not a one-target cap. Preserve already-hit entity IDs, reject duplicate hits and avoid signed-byte overflow. Verify the exact mapped Forge 1.20.1 arrow discard comparison against source at AR3 before code; no Armory gear check or bonus is added in AR0.

### Rain of Arrows — `archers:rain_of_arrows` → `martial_spells:rain_of_arrows`

Tier 4 marksman, physical ranged, sticky AIM target up to 32 blocks. Ten-tick/0.5-second upward pull and release; 15-second cooldown; no authored mana/ammo cost. Source METEOR has launch height 10, horizontal launch radius 2, velocity 1.5, `extra_launch_count=20` = **21 launches**, `extra_launch_delay=5` ticks. Each impact affects radius 1.5 with `0.4 * P` physical-ranged damage and knockback 0.25. No authored pierce/homing/meteor TTL. Release has vertical firework particles and `rain_of_arrows_release`; each glowing `spell_projectile/volley_arrow` has crit/firework travel particles, crit impact, ground decal with crit/poof burst, and `rain_of_arrows_impact` sound.

Use both a server-authoritative delayed meteor scheduler/impact manager **and** tracked visual projectile entities. Exact source launches at release (`t=0`) and `t=5,10,…,100` ticks: 21 total, assuming caster remains alive. The first is centered at the current entity target/location; later launches sample a **uniform random angle on a fixed radius-2 ring**, not a uniform disk. For an entity target, each delayed launch reads its then-current position even if it has moved or died; no target-alive recheck occurs. A removed/unloaded target reference is likewise not reselected, and any successful spawn uses the retained reference's last accessible position. For a location target, the location remains fixed. Thus the Iron's “sticky” selection freezes target **identity or location**, not an entity's release-time position; Spell Engine's sticky AIM fallback itself retains a previous entity only while it is unremoved and still in line of sight. Each spawn starts 10 blocks above its sampled anchor, directed downward at 1.5 blocks/tick, with no authored divergence. FALL projectiles ignore normal block hits and ordinary entity ray hits; they trigger area impact after crossing `0.98 * 10 = 9.8` traveled blocks, snapping back to that distance before impact, about seven movement ticks after spawn at fixed speed. A special reverse collision checker can end a fall early. The falling projectile has a 1200-tick safeguard; once released, its motion is neither gravity nor drag adjusted. The first projectile alone receives the entity as a followed target under the generic default and may turn by the default 1 degree/tick; subsequent ones do not. Active source projectiles discard if their current chunk is not loaded or their owner entity is removed. These are falling spell projectiles, **not** player-fired `AbstractArrow`s, so use P once and do not get Apothic arrow-join scaling, bow enchantments or ammo cost. The source's world scheduler stores runnable callbacks only in memory; pending launches disappear on world reload, and projectile NBT does not preserve traveled distance/range/followed target. Persisting pending jobs and full projectile state locally is an **intentional target robustness divergence**. `JudgementImpactManager` is a useful timed-impact precedent, but Rain needs repeated launches and source geometry.

### Magic Arrow — `archers:magic_arrow` → `martial_spells:magic_arrow`

Tier 4 nature, physical ranged, AIM target, base range 16 plus charge bonus up to 48 (full 64), eight-second cooldown. `SpellBuilder.Casting.charge(spell, 1F)` generates a **one-second reference charge**, not the legacy Forge JSON's fixed cast. With source cast haste `H`, the reference length is `round(20/H)` ticks. At release, `r = min(elapsedTicks / referenceLength, 1)`, with default **linear** curve; release below `r=0.2` fizzles without delivery or cost, while holding beyond full charge keeps `r=1` until released/cancelled. The default `output_scaling=1` makes innate damage/knockback factor `r` (`1 - 1*(1-r)`); authored charge range is `16 + 48r` blocks in the unmodified case. Partial and full successful releases incur the same eight-second base cooldown and one arrow spell-item cost. Cast uses archery pull/ranged weapon animation, generic wind-charging sound and nature sparks at launch; successful release uses archery release, `archers:magic_arrow_release` and two nature-spark circles. One local spell projectile has velocity 1.5, homing angle **2 degrees/tick**, `pierce=99999` (operationally up to 99,999 continuations after successful distinct-target impacts), damage `1.2 * P * r` before target defenses, knockback `2 * r`, 1.2-scale radiating source model, light level 10, double-helix nature travel particles/firework and burst/`magic_arrow_impact` on hit. No area/summon or authored TTL; Spell Engine's hard projectile age safeguard is 1200 ticks. An arrow item is required and `Cost.Item.consume=true` by default, so one is consumed on successful delivery except creative/Infinity/config exemptions.

Use Iron's cast UI with a **custom held-charge state and release calculation**, plus a local tracked projectile and server hit-set. Ordinary `AbstractArrow` byte pierce cannot encode 99999; do not reuse `BarrageArrow` for this. P is sampled at source-equivalent release/impact timing, multiplied once by 1.2 and `r`; the physical-ranged power mapping remains target calibration. On each source tick, the projectile checks range/age before movement, raycasts collision, then turns toward its followed entity by at most 2 degrees, then moves at constant velocity (no motion block means no gravity/drag). A successful entity impact is recorded once per entity ID and decrements pierce; failed impacts are not recorded and may be retried. Ordinary blocks terminate flight; irrelevant targets pass through under the default server config. It discards if its current chunk is unloaded or the owner entity is removed. The source flight range is set to `16+48r` at launch, while general spell-specific range modifiers can alter targeting separately. Source NBT saves owner through superclass plus spell ID, context, perks, behavior/model/scale, but omits remaining range, distance traveled, hit history and followed target; after reload those runtime fields reset (range defaults to 128), so a previously hit entity can become eligible again if flight survives reload. Target persistence of the full flight state is an **intentional robustness divergence**. Current `MagicArrowClientVisuals` is only pose infrastructure and explicitly names `irons_spellbooks:magic_arrow`; it cannot substitute for this source projectile.

### Spirit Wolf Pack — `archers:spirit_wolf` → `martial_spells:spirit_wolf`

Tier 3 nature, physical ranged, source range field 16, instant `one_handed_healing_release`, `spirit_wolf_summon` sound variants, 45-second cooldown with `haste_affected=false`, no explicit mana/ammo. `SUMMON` creates **two** wolves from placement order front/right/left/back one block around the caster, yaw-aligned and ground-snapped with 0/5/10/15-tick offsets: count two selects **front at 0 and right at 5**. Each has 20-tick spawn, 600-tick active, 20-tick despawn transitions.
